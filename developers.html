Build for Light Kali Packages • APIs • Manifest • Lifecycle Current package bridge reference

A practical reference for creating packages that use the real Light Kali package bridge. This page documents the API surface currently passed to packages, the manifest shape, command registration, lifecycle rules, output classes, and the special FreeUserProxy.js integration.

Start with a package Explore the API
01 / Quick Start

The smallest useful package

Start with a single command and no requested capabilities. The important point is the real package contract: a manifest, an install() function, an uninstall() function, and a package-owned command registered through the bridge.

01 · Quick Start 02 · API Reference 03 · Manifest 03B · Install 04 · Lifecycle 05 · Output & Colors 06 · FreeUserProxy 07 · Troubleshooting
Implementation note: The bridge automatically marks commands registered through api.registerCommand() as package-owned. A package should not try to pass a third source/packageKey options object to that method.
CODE 
(() => {
  'use strict';
  const PKG = 'test';
  const manifest = Object.freeze({
    name: PKG,
    version: '1.0.0',
    description: 'Minimal LightKali test package.',
    author: 'Your Name',
    help: 'test help',
    official: false,
    default: false,
    securityLevel: 'low',
    permissions: Object.freeze({
      storage: 'none',
      cookies: 'none',
      network: 'none',
      filesystem: 'none'
    }),
    commands: Object.freeze([PKG]),
    dependencies: Object.freeze([]),
    entry: 'install'
  });
  const run = ({ args = [] } = {}) => {
    const text = args.length ? `test: ${args.join(' ')}` : 'test: ok';
    return [api.line(text, 'success')];
  };
  let api = null;
  const install = async bridge => {
    api = bridge;
    const registered = api.registerCommand(PKG, {
      description: 'Minimal test command.',
      usage: 'test [TEXT...]',
      aliases: [],
      kind: 'plain',
      run
    });
    if (registered === false) {
      api = null;
      throw new Error('PACKAGE_COMMAND_REGISTRATION_FAILED');
    }
    return [];
  };
  const uninstall = async bridge => {
    (bridge || api)?.unregisterCommand(PKG);
    api = null;
    return [];
  };
  window.__kali_pkg_test = Object.freeze({
    manifest,
    install,
    uninstall
  });
})();
A

What happens here?

The loader verifies that install exists, normalizes the manifest, creates the package bridge, calls install(bridge), and then records the package as installed.

The package command receives an object containing args, raw, tokens, api, and the command context.

B

What should stay out?

Do not duplicate lifecycle output, do not overwrite core commands, and do not assume that manifest permissions automatically create browser or filesystem capabilities.

The current bridge exposes capability namespaces, but their operations are still denied by the runtime.

02 / Package Bridge

Every API currently exposed to a package

This is the package-facing bridge, not the larger internal command-service object used by the terminal. Keep package code on this documented surface.

19bridge properties
10direct callable methods
4capability namespaces
01

packageKey

The package's canonical key. Use it when you need to refer to the package itself.

CODE
const name = api.packageKey;
02

manifest

The normalized, frozen manifest associated with the package. It is safe to read, not to mutate.

CODE
const version = api.manifest.version;
const commands = api.manifest.commands;
03

record

The current package registry record passed by the package manager. Treat optional fields defensively.

CODE
const status = api.record?.status ?? 'unknown';
04

append(entries)

Append prepared terminal entry objects after lifecycle output blocking is no longer active.

CODE
api.append([api.line('Runtime event.', 'output')]);
During install/uninstall lifecycle phases, package output is intentionally blocked.
05

line(text, class)

Create one terminal line entry. Text is escaped by the runtime before rendering.

CODE
const entry = api.line('Hello LightKali', 'success');
return [entry];
06

spacer()

Create a blank terminal spacer entry.

CODE
return [api.spacer(), api.line('Next section', 'accent')];
07

snapshot()

Get a runtime snapshot containing mode, cwd, history, registered commands, installed packages, security state, and package records.

CODE
const snapshot = api.snapshot();
const currentMode = snapshot.mode;
const currentPath = snapshot.cwd;
const installed = snapshot.installed;
const commands = snapshot.commands;
08

getMode()

Read the active virtual mode. Current values are user, root, and ghost.

CODE
const mode = api.getMode();
console.log(mode);
09

registerCommand(name, meta)

Register a package-owned command. The bridge injects the package source and package identity automatically.

CODE
api.registerCommand('test', {
  description: 'Run the test command.',
  usage: 'test [TEXT...]',
  aliases: [],
  kind: 'plain',
  run: ({ args = [] } = {}) => [
    api.line(
      args.length ? args.join(' ') : 'test: ok',
      'success'
    )
  ]
});
10

unregisterCommand(name)

Remove a command and its package-owned aliases when you are cleaning up.

CODE
api.unregisterCommand('test');
11

registerPackageGuard(name, guard)

Reserved for the official security package. Normal packages cannot register package security guards.

CODE
api.registerPackageGuard('example', guardFunction);
A normal package receives an error if it attempts to use this capability.
12

unregisterPackageGuard(name)

Reserved for the official security package for removing a package security guard.

CODE
api.unregisterPackageGuard('example');
A normal package cannot unregister package security guards.
13

confirm(title, detail)

Open the terminal's Y/N confirmation flow and resolve to a boolean result.

CODE
const approved = await api.confirm(
  'Allow operation?',
  'The user must answer Y or N.'
);
if (!approved) {
  return [api.line('Declined.', 'muted')];
}
return [api.line('Confirmed.', 'success')];
14

permissions

Read the bridge's capability declaration. In the current package bridge, all four values are fixed to none.

CODE
const perms = api.permissions;
// storage/cookies/network/filesystem are currently 'none'
15

storage

Capability namespace with get, set, remove, and keys methods. In the current bridge, these methods deny access.

CODE
try {
  await api.storage.get('key');
} catch (error) {
  // Storage access denied.
}
This is an exposed namespace, not a currently granted browser-storage API.
16

cookies

Capability namespace with get, set, and remove methods. In the current bridge, these methods deny access.

CODE
try {
  await api.cookies.get('session');
} catch (error) {
  // Cookies access denied.
}
Do not treat the manifest request as an automatic cookie grant.
17

network

Capability namespace with fetch and request methods. In the current bridge, these methods deny access.

CODE
try {
  await api.network.fetch('https://example.com');
} catch (error) {
  // Network access denied.
}
The package bridge does not currently grant these methods.
18

filesystem

Capability namespace with read, write, remove, and list methods. In the current bridge, these methods deny access.

CODE
try {
  await api.filesystem.read('/home/kali/file.txt');
} catch (error) {
  // Filesystem access denied.
}
The terminal has a virtual filesystem internally, but this package bridge does not currently grant direct filesystem operations.
19

flow

The low-level flow surface exposed by the bridge. The current bridge provides passthrough/stub behavior here; use confirm() for the supported Y/N confirmation flow.

CODE
const flow = api.flow;
const context = { step: 'example' };
const started = flow.begin(context);
const next = flow.next('input');
const resumed = flow.resume();
const cancelled = flow.cancel();
Current bridge behavior is: begin(x) → x, next(x) → x, cancel() → null, resume() → null. Do not treat it as a general flow engine.
Command metadata

Plain and flow commands

Command registrations support description, usage, aliases, kind, and the execution callbacks run or flow callbacks begin, next, cancel, and resume.

Plain command

CODE
api.registerCommand('test', {
  description: 'Run the test command.',
  usage: 'test [TEXT...]',
  aliases: [],
  kind: 'plain',
  run: ({ args = [] } = {}) => [
    api.line(
      args.length ? args.join(' ') : 'test: ok',
      'success'
    )
  ]
});

Flow command

CODE
api.registerCommand('login-demo', {
  description: 'Example flow command.',
  usage: 'login-demo',
  aliases: [],
  kind: 'flow',
  begin: ({ api }) => {
    return api.confirm(
      'Continue?',
      'This starts a Y/N confirmation flow.'
    );
  },
  next: async ({ api, input }) => {
    return [
      api.line(`Input: ${input}`, 'muted')
    ];
  },
  cancel: () => [
    api.line('Cancelled.', 'muted')
  ],
  resume: () => [
    api.line('Waiting for input.', 'muted')
  ]
});
03 / Manifest

Package identity and permissions

The runtime normalizes the fields shown below. Unknown fields are not part of the documented package manifest contract, so keep your manifest focused and explicit.

CODE
const manifest = Object.freeze({
  name: 'test',
  version: '1.0.0',
  description: 'Minimal LightKali test package.',
  author: 'Your Name',
  help: 'test help',
  official: false,
  default: false,
  securityLevel: 'low',
  permissions: Object.freeze({
    storage: 'none',
    cookies: 'none',
    network: 'none',
    filesystem: 'none'
  }),
  commands: Object.freeze(['test']),
  dependencies: Object.freeze([]),
  entry: 'install'
});

Important about permission values:The current implementation does not define a finite enum such as read/write/full. It converts each permission value to lowercase text and defaults to none. More importantly, the package bridge currently fixes api.permissions to none for every category and replaces all capability operations with denied functions. Therefore, do not document or rely on values such as read, write, or full as working grants in the current runtime.

01

What “accepted” means

The normalizer stores a lowercase string. That is different from having a runtime allow-list. The current source does not validate these four fields against a closed set of capability values.

02

What “granted” means

A grant would require a capability implementation behind the bridge. Right now every capability method supplied to a package throws an access-denied error.

03B / Package Installation

How users install packages

Developers create and publish the package source. The LightKali package manager controls how that source is loaded. For an external package, users provide an HTTPS URL directly to the package manager.

External package ruleExternal package installation uses apt install https://.... The external source must be HTTPS. Do not document http:// as an external package installation method.
USER COMMAND
apt install https://example.com/path/to/test.js
What the developer does not controlThe developer does not bypass package-manager validation, choose the user's trust decision, or replace the Core's external-source security process. The package should simply expose a valid package module and manifest.
Package scope

Build the package, define its manifest, register its own commands, keep package-local state, and handle cleanup.

Core boundary

Do not depend on undocumented Core internals or assume that a manifest permission string creates a working capability.

External source

For external installation, use a real HTTPS package URL. The package manager remains responsible for loading and security checks.

04 / Lifecycle

Install, run, uninstall

Lifecycle hooks are for setup and teardown. The Core owns lifecycle status output and blocks package transcript output while install/uninstall is in progress.

01

install(api)

Validate the bridge if your package needs to. Store the bridge, initialize local state, register your commands, and return [] on success.

02

uninstall(api)

Unregister package-owned commands and clear package-local state. Return []. Cleanup of the package record and global export remains Core-owned.

CODE
const install = async api => {
  api.registerCommand('test', {
    description: 'Test command.',
    usage: 'test',
    aliases: [],
    kind: 'plain',
    run: () => [
      api.line('test: ok', 'success')
    ]
  });
  return [];
};
const uninstall = async api => {
  api.unregisterCommand('test');
  return [];
};
Do not write lifecycle progress text.There is no need to print “Installing…”, “Installed…”, “Uninstalling…”, or similar messages from install()/uninstall(). The Core handles the installation flow. During those phases, package transcript output is blocked by design.
1

Load

The package loader resolves the package source and requires a valid install function.

2

Normalize

The manifest is normalized and frozen before the bridge is built.

3

Initialize

install(bridge) runs inside the package lifecycle phase.

4

Runtime

The package is recorded as enabled and its commands become part of the command registry.

5

Remove

On uninstall, the runtime calls uninstall(bridge), then unregisters package commands and clears the package module.

05 / Output

Terminal messages and color classes

Use api.line() for ordinary terminal output. The current runtime source confirms these class tokens are actively used by Light Kali. The renderer accepts a CSS class name; there is no central color-enum validator in the package bridge.

CODE
return [
  api.line('Ready.', 'success'),
  api.line('Warning: example warning.', 'danger'),
  api.line('Current path: /home/kali', 'dim'),
  api.spacer(),
  api.line('More information', 'accent')
];
ClassConfirmed usageTypical purpose
outputYesDefault terminal output.
mutedYesSecondary or explanatory text.
accentYesHeadings, confirmations, highlighted status.
dangerYesErrors, blocked actions, warnings requiring attention.
successYesSuccessful result/status.
dimYesLow-emphasis metadata.
purpleYesHighlighted project/information text in current runtime output.
cyan-lightYesHighlighted informational text in current runtime output.
pinkYesUsed by current boot/runtime output.
Do not hard-code a private hex contract.The inspected public stylesheet does not define the terminal color palette as a single documented enum. Treat the class tokens above as the usage vocabulary currently evidenced by runtime code, not as a promise that every arbitrary class name has a predefined visual color.
06 / Special Integration

FreeUserProxy.js

Light Kali has a special plugin named FreeUserProxy.js that exposes working proxy templates and randomized User-Agent values for browser-side integrations. The plugin exports itself as window.__FreeUserProxy and globalThis.__FreeUserProxy.

10User-Agent presets
4+primary proxy templates
fallbackproxy scanning path
Recommended architecture:Prefer a proxy endpoint you control for your application, then use the plugin's currently working list as fallback. Do not send passwords, session tokens, cookies, API keys, or other secrets through public proxy services you do not control.
A

Current plugin API

getRandomUserAgent(), getAllProxies(), getWorkingProxies(), getRandomWorkingProxy(), and isAvailable() are exposed by the plugin object.

B

Availability is asynchronous

The plugin scans its primary proxies first and scans fallbacks when the primary set has no successful candidates. Querying getWorkingProxies() before the scan completes may return an empty list.

1. Small adapter

The current plugin does not define a built-in getFreeUserProxy() function. If you like that helper name, add this adapter:

CODE
function getFreeUserProxy() {
  return window.__FreeUserProxy
    ?? globalThis.__FreeUserProxy
    ?? null;
}

2. Check availability

CODE
function isFreeUserProxyAvailable() {
  const fup = getFreeUserProxy();
  return fup
    && typeof fup.getWorkingProxies === 'function';
}

3. Test your own proxy template

Your template should contain the exact {url} placeholder. The example below uses the same Light Kali test URL pattern used by the plugin and treats HTTP 403 as reachable, matching the plugin's own proxy test logic.

CODE
async function testCustomProxy(
  proxyTemplate,
  testUrl = 'https://LightKali.github.io'
) {
  try {
    if (
      typeof proxyTemplate !== 'string' ||
      !proxyTemplate.includes('{url}')
    ) {
      return false;
    }
    const controller = new AbortController();
    const timeout = setTimeout(
      () => controller.abort(),
      5000
    );
    const url = proxyTemplate.replace(
      '{url}',
      encodeURIComponent(testUrl)
    );
    const res = await fetch(url, {
      method: 'HEAD',
      signal: controller.signal,
      mode: 'cors'
    });
    clearTimeout(timeout);
    return res.ok || res.status === 403;
  } catch {
    return false;
  }
}

4. Build a custom-first + fallback list

Put your own proxy at the front when it passes the connectivity check. Then consume the plugin's working list. This keeps your package independent of a single proxy endpoint.

CODE
const state = {
  customProxy: '',
  workingProxies: [],
  proxyReady: false
};
async function prepareProxyList(
  forceRefresh = false
) {
  if (
    !forceRefresh &&
    state.proxyReady &&
    state.workingProxies.length > 0
  ) {
    return state.workingProxies;
  }
  const fup = getFreeUserProxy();
  if (
    !fup ||
    typeof fup.getWorkingProxies !== 'function'
  ) {
    throw new Error(
      'FreeUserProxy is not available. ' +
      'Please ensure FreeUserProxy.js is loaded.'
    );
  }
  let working = [];
  try {
    working = fup.getWorkingProxies() || [];
  } catch {
    working = [];
  }
  if (!Array.isArray(working)) {
    working = [];
  }
  if (
    typeof state.customProxy === 'string' &&
    state.customProxy.includes('{url}')
  ) {
    const customOk = await testCustomProxy(
      state.customProxy
    );
    if (customOk) {
      const exists = working.some(
        proxy =>
          proxy?.template === state.customProxy
      );
      if (!exists) {
        working.unshift({
          name: 'custom',
          template: state.customProxy
        });
      }
    }
  }
  if (working.length === 0) {
    throw new Error(
      'No working proxies available.'
    );
  }
  state.workingProxies = working;
  state.proxyReady = true;
  return working;
}

5. Rotate through working proxies

CODE
let proxyIndex = 0;
function getNextProxy() {
  if (state.workingProxies.length === 0) {
    throw new Error(
      'No proxy available. ' +
      'Call prepareProxyList() first.'
    );
  }
  const proxy =
    state.workingProxies[
      proxyIndex % state.workingProxies.length
    ];
  proxyIndex =
    (proxyIndex + 1) %
    state.workingProxies.length;
  return proxy;
}

CODE
function selectUserAgent() {
  const fup = getFreeUserProxy();
  if (
    fup &&
    typeof fup.getRandomUserAgent === 'function'
  ) {
    return fup.getRandomUserAgent();
  }
  return (
    'Mozilla/5.0 (Windows NT 10.0; Win64; x64) ' +
    'AppleWebKit/537.36 (KHTML, like Gecko) ' +
    'Chrome/122.0.0.0 Safari/537.36'
  );
}

07 / Troubleshooting

When a package does not install

The package manager classifies common failures using explicit error codes. Use the code first, then fix the underlying package issue rather than adding random runtime workarounds.

PACKAGE_ENTRY_INVALID
The loaded package does not expose a callable install function. Check the final exported object and make sure the loader can resolve the package module.
PACKAGE_SYNTAX_ERROR
The package source could not be evaluated because of JavaScript syntax or evaluation failure. Validate the exact source being loaded.
PACKAGE_SOURCE_HTML
The remote source returned HTML instead of JavaScript. The URL should resolve to the actual package source rather than a web page or error document.
PACKAGE_SOURCE_UNAVAILABLE
The package source could not be fetched. Check HTTPS, reachability, CORS behavior, and the final resolved URL.
PACKAGE_SECURITY_BLOCKED
The package was rejected by the current security layer or guard path. External package sources can be inspected before execution and may require explicit trust/confirmation.
PACKAGE_COMMAND_REGISTRATION_FAILED
A command could not be registered. A common cause is trying to replace a command already owned by the Light Kali core. Use a unique package command name and register it through api.registerCommand().
PACKAGE_MANIFEST_INVALID
The package identity or manifest normalization path failed. Check name, entry, and the package's exported manifest object.
PACKAGE_HTTPS_LOAD_FAILED
The external HTTPS package load failed. Verify the HTTPS endpoint and the returned source.
PACKAGE_INSTALL_FAILED
A package failure did not match one of the more specific classifications. Inspect the package's install path, command registration, manifest, and source resolution together.
Why does my package's install message not appear?
That is expected. The runtime blocks package transcript output while install and uninstall lifecycle phases are active. Return an empty array from the lifecycle hook and let the Core own lifecycle reporting.
Why does api.network throw even when I requested network permission?
Because the current package bridge exposes the namespace but supplies denied implementations for fetch and request. Manifest normalization alone does not create a runtime grant.
Can a normal package register a security guard?
No. The current bridge restricts package security guard registration and removal to the official security package.
Developer rule of thumb

Build on the bridge. Let the Core own the system.

Keep package state local, register only package-owned commands, use the documented bridge surface, return clean lifecycle results, and treat capabilities as unavailable unless the current runtime explicitly implements them. That approach keeps packages aligned with the actual Light Kali package manager.
